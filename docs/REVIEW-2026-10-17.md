# Collab: live product, UX and implementation review

Reviewed 17 October 2026. This is an expert heuristic review with live interaction and source inspection, not a user study or security certification.

**Verdict: a substantial working agent-commerce prototype with a credible narrow use case, but an overly broad product promise and important trust and journey gaps.** Its strongest value is reducing the work between a customer asking a question and a merchant confirming an actionable order or appointment. Its weakest area is helping a first-time user reach that value without understanding agents, permissions, model setup and multiple overlapping states.

| Dimension | Judgment / 10 | Reason |
|---|---:|---|
| Technical prototype | 8 | Real live drafting, matching, slot holds, simulated payment and browser signature verification; substantial guardrail and integration tests |
| Visual consistency | 7 | Coherent dark/pink style, recognizable controls and consistent cards; dense text and many competing actions |
| User experience | 5 | Successful core journey, but duplicate goals, premature agreement state, setup barriers and weak navigation feedback |
| Immediate adoption readiness | 4 | No evidence of marketplace liquidity or retention, guest value is delayed, seller onboarding is substantial, payment is simulated |
| Potential differentiated value | 7 | Owner-controlled agent collaboration plus availability and execution is useful; broad chat and catalogs alone are insufficient |

Scores are subjective reviewer judgments, not measured conversion rates or completion percentages.

## Highest-priority findings

### P0 — Simulated payment is presented as real payment

After clicking Pay for the demo service, the live app said “You paid ₹450/session”; the pass said “Paid”; the receipt and public verifier said “Paid in the app.” Even the expanded AP2 explanation did not plainly state that no money moved. Internally, `core/pay.ts` and `core/ap2.ts` explicitly use `mode: "test"`; `web/js/gpay.js` uses Google Pay TEST.

**Change:** persistent “Demo — no money moves” disclosure in the checkout, action label, success state, pass, receipt and public verifier. Keep simulated activity out of real merchant reputation and financial totals. Acceptance: a first-time tester can explain whether money moved without opening developer details.

Relevant files: `web/js/cards.js`, `web/js/pass.js`, `web/js/verify-page.js`, `web/js/gpay.js`, `server/src/core/pay.ts`.

### P1 — Booking time is outside the signed agreement

The live booking pass showed the selected appointment, but the public verifier omitted it. Source confirms `sealed()` hashes offer terms, parties, task and agreement time, without the reservation slot. The slot endpoint changes `e.reservation` after agreement; cart/AP2 code does not include it either. A valid agreement signature therefore does not attest to the booked time.

**Change:** include resource, slot start/end and timezone in a versioned signed commitment before final confirmation, or issue a signed amendment linked to the original agreement. Verify these fields publicly. A meaningful regression test should demonstrate that changing the booked time invalidates the relevant signed commitment.

Relevant files: `server/src/core/deals.ts:130`, `server/src/server.ts:1248`, `server/src/core/pay.ts`, `web/js/verify-receipt.js`.

### P1 — One user intention becomes two goals

The live Requests screen showed both “Men's Haircut in Indiranagar — DRAFT, No conversations yet” and the booked haircut goal. The instant-book handler calls `/api/people/:handle/order` without linking the existing brief; negotiation uses the brief-specific engagement endpoint.

**Change:** pass the originating goal/brief into direct ordering and attach the resulting task to it. Keep one goal with a continuous timeline. Also prevent repeated taps on the still-visible Book button from accidentally starting another purchase.

Relevant file: `web/js/app.js:901` and the order route in `server/src/server.ts`.

### P1 — A promoted first-use feature requires a large model setup

Saving a note worked; asking about it returned a Gemma download/device message instead of the answer. Settings states a one-time 2 GB download, and cross-device use requires Google sign-in plus another open configured device. These are significant prerequisites for someone who has just clicked “Remember” or “Your context.”

**Change:** let users immediately search and read their notes locally without generation. Show matched notes with provenance, then offer optional device generation or an explicitly chosen cloud mode. Avoid making model setup part of the default purchase journey.

### P1 — Privacy claims need separate storage, processing and disclosure explanations

The headline and footer use absolute wording. Current source stores private facts in the account on the server; default inference is restricted to personal devices, while settings allow cloud processing. “Not shared with another person's agent” is a useful boundary, but it is different from “never leaves the device” or server blindness. The public rounded budget also communicates willingness to pay even when the exact limit is withheld.

**Change:** concise, consistent labels for Stored where / Processed where / Shared with whom; show the exact outgoing brief before sending. Avoid implying encryption of stored private facts from encrypted device-to-device transport alone.

### P2 — The UI presents system structure before user outcomes

Context, Sharing, agent addresses, A2A, engine labels and multi-goal controls are prominent. In the live mobile view, result cards contained several competing actions, while status messages used generic terms such as “Agreed,” “Receipt,” and “handover.” A haircut buyer needs merchant, service, time, price, status and one next action.

**Change:** a customer home with “Find/book,” “My bookings/orders,” and “Saved details”; a merchant home with “Today's requests,” “Offerings/availability,” and “My storefront.” Keep advanced agent controls accessible behind progressive disclosure. Use domain language: “Choose a time,” “Booking confirmed,” “Check in.”

### P2 — Navigation briefly displays the previous screen under the new title

Observed repeatedly when moving between People, Sharing and Requests. `paintHeader()` changes the title before the asynchronous screen HTML is ready. This creates misleading intermediate UI and can leave old actions in view.

**Change:** loading/skeleton state scoped to the destination, cancel or discard outdated renders, then commit header and content together. Preserve input focus and scroll intentionally.

### P2 — Accessibility and forms need a dedicated pass

The seller form contained inputs, selects and textareas without associated labels or `aria-label`; several fields appeared unnamed in the accessibility tree. The menu control was exposed as “☰.” Checkboxes and some text fields were better labelled, so the issue is inconsistent rather than universal.

**Change:** persistent programmatic labels, descriptive menu names, focus behavior for all dialogs, keyboard operation and adequate contrast. Run automated checks plus a manual screen-reader journey. No formal WCAG compliance claim is made here.

### P2 — Availability of features and deployment evidence is unclear

Communities has code but no navigation entry. Historical docs simultaneously describe missing features and later additions. The deployed build identifies itself as dirty. This makes “implemented,” “discoverable,” “tested,” and “deployed” easy to confuse.

**Change:** immutable build manifests, per-feature release status, staging smoke tests and one authoritative current-state document. Maintain a visible feature matrix internally with a reproducible test for each supported workflow.

## Technical implementation assessment

The separation of AI proposals from deterministic checking is a sound foundation. The system has meaningful modules for policy, resource holds, payment claims, signatures, task recovery and connector events. Automated coverage includes concurrent last-unit holds, overlapping slots, budgets, revocation, replay, private processing modes and tampering. The live verification flow is real functionality, not just a decorative “verified” badge.

The principal maintenance risk is concentration of behavior in large files: roughly 1,622 lines in the server entry point, 1,126 in app.js, 823 in screens.js and 701 in cards.js during this review. Template strings and repainting can work, but journey state, rendering and event handling are coupled. Refactor around booking, ordering, context, permissions and account workflows; introduce explicit contracts and state transitions before undertaking an arbitrary framework rewrite.

Source queries also have fixed collection caps (for example, track record derives from up to 300 engagements). This can eventually produce incomplete history rather than a trustworthy lifetime record. Use pagination and durable aggregates with explicit reconciliation. No large-scale load claim is supported by this review.

Live health reported Model Armor `failMode: open`. That means outages can allow text through that optional screen while deterministic policy still applies; it is not evidence that all privacy controls disappear. Decide and test the desired behavior for sensitive workflows, alert on unscreened traffic and document the product implication.

The signing authority is Collab's server acting for agents. Explain this honestly: it attests to Collab's record, not an independent human signature, actual payment settlement, or physical fulfilment.

### What the tests do and do not prove

The first suite run failed the public-track-record assertion. The assertion scans serialized output with `/Record Buyer|tr-buyer|450|1350/`, including the `since` timestamp. At the initial run time, timestamps could contain the numeric price substring `450`. The targeted retest and final full suite passed; the separately inspected local record contained no buyer or price fields. This strongly suggests a time-sensitive assertion, but it should be fixed with field-specific checks rather than dismissed without inspection.

The repository's `live-cases.ts` script explicitly targets **real Gemini**. I additionally ran its 12 cases once against a fresh fake-model server to examine offline coverage. Five reached agreement, only four without the script's boundary flag; seven missed/errored. The vehicle case produced 7 instead of a lakh-scale price, and the script printed `$NaN` and labelled fake calls as Gemini calls. These are **offline harness/model compatibility results, not production Gemini success rates**. They expose a gap in trustworthy local end-to-end coverage. Retain deterministic tests, but add a separate real-model acceptance suite for every advertised category, language and monetary format.

## Value and adoption

The best initial proposition is: **“Let customers ask, book and collect from your shop without repeated calls or messages.”** It has a specific buyer, a visible before/after, and a distribution surface—the merchant's QR or shared link. Start with one local service or retail workflow and a small, dense group of merchants.

Chat, catalogs and order capture are already familiar alternatives: WhatsApp Business offers catalogs and order-oriented business features ([official feature page](https://whatsappbusiness.com/products/business-app-features/)); Urban Company offers men's grooming booking ([official service page](https://www.urbancompany.com/near-me/mens-grooming-near-me)). This comparison supports a product inference, not a measured market-size claim: Collab must prove fewer owner interruptions, more reliable availability and faster completion to justify a new habit.

The differentiator is the combination of permitted knowledge, owner-defined authority, checked commitments and a clear escalation path. A2A is useful infrastructure; consumers are more likely to care that they get an answer and an appointment. Automatic bargaining should be optional because some merchants want fixed prices and fewer negotiations.

I found no evidence in this review for active-user counts, retention, conversion, merchant willingness to pay or market liquidity. A demo result plus a sparse second match is not enough to infer the whole marketplace's size. The adoption score reflects observed friction and missing validation, not a claim that demand does not exist.

## Improvement sequence and acceptance criteria

| Priority | Deliverable | Observable success |
|---|---|---|
| First | Honest test-payment labels everywhere | Users correctly state that no money moved before tapping Pay |
| First | One goal per journey; signed slot/time | One request yields one tracked goal; signed record includes actual commitment details |
| First | Outcome-led landing and merchant preview before signup | New users can explain the value and see a merchant's offering without learning agent vocabulary |
| Next | Guided merchant setup | Offering, price, stock/hours, terms and preview completed without developer assistance |
| Next | Immediate notes search and accessible controls | Saved notes usable without model download; keyboard and screen-reader journey succeeds |
| Next | Clear domain status and one primary action | Users identify the current state and required next action without opening logs |
| Next | Category-specific live acceptance tests | Repeatable outcomes for quantities, currencies, lakh notation, language, empty supply and unavailable stock |
| Before scaling | Real settlement integration and operational recovery | Reconciliation, reversals, refunds and failure recovery demonstrated in a payment-provider sandbox before launch |
| Before scaling | Actual device/integration validation | Push, camera, PWA, device relay, POS/calendar and restart recovery proven with supported setups |

For a pilot, measure onboarding completion, time to first useful answer, request-to-confirmed-booking conversion, owner interventions per order, abandonment by step, fulfilment rate, repeat usage, and cost per completed outcome. Segment demo and real data. Proposed research: observe five new customers and five merchants completing realistic tasks; then run a small multi-week merchant pilot. These are suggested validation activities, not results already achieved.

The live audit account, a clearly labelled test draft, sample private note and paid-in-test demo booking remain for inspection. No production listing was published. Physical fulfilment and merchant notification delivery were not claimed or tested.
